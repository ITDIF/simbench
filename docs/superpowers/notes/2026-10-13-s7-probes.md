# S7（S7comm / ISO-on-TCP）技术前提实测记录（2026-10-13）

跑在：Windows + Python 3.13 + `python-snap7==1.3`（**自带的 `snap7/lib/snap7.dll`**，x64）。
用途：`docs/superpowers/plans/2026-10-13-s7-server.md` §2 的每条结论的出处。
探针脚本：同目录 `s7_probe_server.py`（可重跑）。

## 0. 怎么把探针环境搭起来（真实的坑，先记下）

```powershell
# python-snap7 3.x 的 wheel 是纯 ctypes 包装，**不含原生库**（实测 34 个条目、0 个 .dll/.so）
# python-snap7 1.3 的 win_amd64 wheel 自带 snap7/lib/snap7.dll（150 KB）——探针与以后的依赖都从它取
python -m pip download python-snap7==1.3 --no-deps -d .
python -m venv %TEMP%\s7venv
%TEMP%\s7venv\Scripts\python -m pip install python_snap7-1.3-py3-none-win_amd64.whl
# 1.3 的 __init__ 会 `import pkg_resources`，而 setuptools>=81 已移除它（实测 84.0.0 报
# ModuleNotFoundError）——必须钉 setuptools<81
%TEMP%\s7venv\Scripts\python -m pip install "setuptools<81"
```

结论：**走 snap7 这条路，仓库要随包放一份 `snap7.dll`（LGPL-3.0）**；1.3 那份 wheel 是最省事的
来源（PyPI 上有，x64 Windows），或者从 snap7 官方源取对应平台的库。

## 1. `Server.register_area(area, index, buffer)` 的语义（**不是**我最初猜的那样）

`python-snap7 1.3` 的 `server/__init__.py`：`Srv_RegisterArea(pointer, area_code, index,
byref(userdata), size)`，`userdata` 必须是 **ctypes 缓冲**（`(ctypes.c_ubyte * n)()`），
传 `bytearray` 会在 `ctypes.sizeof` 上炸。

`index` 是**区域编号**，对 DB 区就是 **DB 号**。实测：

```
register(DB, index=1, buf) -> None
register(DB, index=2, buf2) -> None        # 第二个 DB 也能挂
读 DB1[0:2] -> 41 48                        # 我们初始化的 12.5f
读 DB2[0:2] -> 10 a0                        # 另一个缓冲（内容随它）
读 DB3      -> RuntimeError: b'CPU : Item not available'   # 没注册的 DB
```

**所以"snap7 服务端只能服务一个 DB"是错的**（我中途这么猜过，被这条探针推翻）：多 DB、
MK/PE/PA 都能分别 `register_area` 挂上，没注册的区域/DB 回 `Item not available`（正是"未定义
地址"该有的形状）。

## 2. 读写往返与"引擎侧写缓冲"（值归属与波形的落点）

```
主站写 DB1[4:6] -> 服务端 ctypes 缓冲立刻变成 ab cd      # 主站写能被我们看见（缓冲共享）
引擎侧直接写缓冲[8] -> 主站读回 55                        # 波形 tick 往 S7 区写 = 改这块缓冲
CPU: S7CpuStatusRun | PDU: 480                          # 会话与 PDU 长度都正常
MK 读 4B / PE 读 4B                                      # I/Q/M 区各自独立
```

⇒ 与 Modbus 那套同构：**"我们这边的写"就是改共享缓冲，"主站的写"落进同一块缓冲**。
值归属（谁接管了哪一段）在 S7 这一侧要靠 `set_read_events_callback` /
`set_events_callback` 的事件（`EvtCode/EvtParam1..4/EvtRetCode`，实测字段名如此；
`EvtParam` 这个字段不存在，写错了 ctypes 会静默吞掉回调异常）。

## 3. 两条硬限制（决定计划怎么写的）

1. **拿不到原始字节**：snap7 的原生服务端只在 DLL 内部组帧，回调给的是**事件**（谁读了/
   写了哪个区哪一段），没有 TPKT/COTP/S7 的原始 hex。⇒ 报文窗在 S7 通道上给不了"原始字节"
   这一列（要真 hex 得自己在 TCP 层再抄一份 TPKT/S7 解析，或干脆自研协议栈）。
2. **协议栈是 C 库**（LGPL-3.0）+ 平台相关二进制：仓库要么随包放 DLL，要么写一份"先下载/
   安装"的说明；打包（PyInstaller）时还得把它算进 hidden/数据文件。

## 4. 另一端：有没有纯 Python 的 S7 客户端可以当验收主站

`pip download pys7` → `pys7-3.1.1-py3-none-any.whl`，**20 个条目、0 个原生库**（纯 Python），
模块是 `pyS7/client.py` / `async_client.py` / `address_parser.py` —— 它是**客户端**。
⇒ 自研 S7 服务端那条路（方案 B）的自动化验收有主站可用：`pys7` 当主站，snap7 的客户端当
第二个独立主站（两份实现同时通过，兼容性证据比只对一个强）。

PyPI 上没有现成的纯 Python S7 **服务端**（`s7comm` / `s7server` / `s7-server` 都
"No matching distribution"），所以方案 B = 自己写协议栈。
